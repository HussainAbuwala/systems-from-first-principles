# e08-06: investigation of the start-of-run freeze (E08, stage 7)

**Purpose:** find out who holds the database's write lock for seconds after a fresh full copy, in which step, and why. Tool: `load/lock-probe.mjs` on `sfp-app` every 250 ms (tries the write lock with no waiting, records Litestream's `/debug/sync-status`, per-disk I/O for the server disk `sda` and the Volume `sdb`, Litestream's CPU, and a goroutine dump whenever the lock has been held over 500 ms). Report: `load/lock-probe-report.py`.

**What actually ran (two mistakes in my script):** the probe was started with `nohup … &` over SSH without detaching its input, so the SSH call waited for it: it recorded 10:53:30–11:04:31 UTC, which covers the fresh full copy and both whole-copy merges, but **with no traffic**. The wait for "snapshot complete" then looked only 6 minutes back, missed it and timed out, so the E08 load started at 11:14:49, 20 minutes after the copy, with no probe running. That load run passed (create p99 30.8 ms, redirect p99 18.8 ms, 0% errors, counts exact). A final `pgrep -f` loop matched its own command line and never ended; stopped by hand; the load machine was deleted by the watchdog at 11:54 (2 h billed).

**Finding: the write lock was held for 30.5 s, once, at about 10:56:14–10:56:44**, 28 s after the full copy finished (10:55:46). Throughout, Litestream reported `sync/verify (active)`; server disk idle, Volume about 6 MB/s writes and 2% busy, Litestream about 123% of a core. All 28 goroutine dumps show the same stack: `syncOnce → syncLocked → checkpointIfNeeded → checkpointWithExecutor → verifyAndSyncWithExecutor → verifyWithExecutor → lastPageMatch → ltx.Decoder.DecodePage` (and CRC hashing). In Litestream 0.5.17 `lastPageMatch` checks that the WAL's last synced page is in the **most recent LTX file** by decoding that file page by page from the start. Right after a fresh full copy, with no writes since, the most recent LTX file is the full copy itself (1.7 GB compressed, 100 M links), so a passive checkpoint holds the write lock (its `_litestream_lock` barrier) for about 30 s of CPU work. **Not disk:** the earlier explanation in the stage log ("the disk is saturated") was wrong.

**This explains every run:** `e08-03` (traffic began 21 s after the copy; the first checkpoint scanned the full copy; the app's saves waited, freezing Node); `e08-04` and `e08-05` (traffic began within a second, click-count saves created small LTX files at once, so the first checkpoint verified a small file); `e08-06` (the 30 s lock happened with nobody there). Likely real-life trigger: a fresh full copy followed by a quiet spell, e.g. a recovery at a quiet time. Scales with database size (about 30 s at 12 GB). Not found as a known Litestream issue (search 2026-10-07).

Also checked: after a recovery Litestream also writes the whole database again (on the `e07-05` rebuilt server: a 169 MB level 1 file 43 s after Litestream started, the whole 10 M database), so a recovery can be followed by the same scan.
